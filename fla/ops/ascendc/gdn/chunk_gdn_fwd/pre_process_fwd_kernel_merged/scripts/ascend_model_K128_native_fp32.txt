[1] 每步 Cube 拍数(16x16 粒度, FP32 乘按拆分倍数计)
    h program:  256 拍   w@h=128 + kT@v=128
    m program:  512 拍   kT@w=256 + M@m(fp32)=256
    上游分流: 每 head 2+2 个 program, 共 128 个, 铺在 28 个 AIC 上 = 4.57 波

[2] 串行纯计算下界 vs 吞吐下界(只算 Cube 拍, 不含访存/同步/流水气泡)
    上游分流  串行链 176 x max(256,512) = 90112 拍 =     54.6 us
              总算力     8.65 M 拍 / 28 AIC =     0.31 M 拍 =    187.2 us
    -> 上游分流在昇腾上受吞吐限制 (吞吐/串行 = 3.43x)
    合并式    串行链 176 x 1280 = 225280 拍 =    136.5 us   w@h=256 + kT@[v|w]=512 + M@m(fp32)=512
              总算力    156.0 us
    -> 合并把串行链变成 2.50x, 总算力变成 0.83x

[3] 片上容量(单 program 每步的峰值需求, 对比 950PR 物理容量)
    program          L0A       L0B       L0C(累加器合计)   判定
    h              16.0K     16.0K            48.0K   OK
    m              64.0K     32.0K            96.0K   OK
    merged         64.0K     64.0K           224.0K   OK

[4] 读入流量(bf16 输入)
    唯一数据    48.0 KB/head/步
    上游分流    830.5 MB = 3.00x  (DRAM 下界   553.6 us)
    合并式      276.8 MB = 1.00x  (DRAM 下界   184.5 us)

[5] AIC / AIV 配比(950PR 为 1:2)
    h program: Cube 256 拍 + Vector(减法/decay 缩放/BF16 转换, 约 4 x BT x BS 元素)
    m program: Cube 512 拍 + Vector(对角构造/取负, 约 K x BS 元素)
    -> m 的 Cube 负载是 h 的 2.0x, 但 Vector 负载远轻; 按列块分流时两类 program 的 AIC/AIV 利用率不均衡

[6] H20 实测(仅参考, 不参与上面的结论)
    model-g default      1549.9 us   每步  8.81 us
    model-gk default     1608.8 us   每步  9.14 us
    model-dplr default   1609.6 us   每步  9.15 us
    H20 峰值 BF16 约 148 TFLOPS(78 SM), 实测有效算力 43~51 TFLOPS = ~30%,
    且其耗时远高于自身 Cube 下界 -> H20 上是延迟受限。
    昇腾这边吞吐下界反而高于串行纯计算下界 -> 结论方向不同, 不能照搬。
